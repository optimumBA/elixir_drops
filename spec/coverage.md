## Composition and bounds

`system` imports the actual `app` and `delivery` definitions rather than copying their
logic. It checks aligned saved content/code revisions, published targets for jobs,
and no derived work from rejected saves while identity/comment actions and background
work interleave. It uses three users/devices/Drops and six comment slots. `app` alone
uses four Drops; `delivery` alone uses three. `discovery` uses six catalog items/queries,
two-card abstract pages and externally supplied rank/matching classes. `sponsors` uses
two mounted views, three Drops and two actual placements. `http` enumerates request
classes. Scalar clocks/versions/counts can grow, but each simulation has a step limit.
These are finite data abstractions, not exhaustive production state-space exploration.

The discovery/HTTP/sponsor models are projections with explicit admission inputs;
they are not mechanically composed with every identity/cache state. The composed
model assumes a successfully saved content projection and successful queue admission,
while delivery separately exposes ignored enqueue failures. No global proof covering
all parser, SQL, network, storage and browser states is claimed.

Model tests validate the model. An application-specific Elixir replay driver does not
exist in this deliverable. A future conformance harness must map model IDs to real
records/session tokens, action parameters to app entry points, and expected state to
persisted/queryable values. It must fail on recorded implementation gaps; calling
contexts directly can bypass authorization enforced at a web boundary.
