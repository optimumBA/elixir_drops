# Reveal the selected public discussion reply

Slug: reveal-profile-reply-on-mobile
Model: not applicable — repair how an existing discussion is revealed on entry, without new persistent state or business rules

An anonymous visitor who selects **View in discussion** on a contributor's Comments tab sees the exact selected public comment or reply on the Drop, including older conversations. Opening the same reply URL by full-document navigation also reveals it without a second action. This must work at both viewports in Acceptance. Back after either tested journey returns to that contributor's Comments. Reuse the discussion's existing reply area, controls and scroll behavior; replace the dependency on receiving a LiveView navigation event for initial document entry. Do not redesign the profile or discussion, change URL/link semantics or permissions, or alter feed batching, visibility, continuity or the other original Issue obligations.

Build in the isolated checkout. Run the existing setup separately from Cucumber, including the compiled test application and repo-pinned Chromium 1193; keep all configured checks and native bounds. Attach executed candidate evidence to the native Build: candidate revision, actual one-run acceptance command and elapsed time, per-mode/per-viewport href, exact rendered body, uniqueness, computed visibility, viewport and Back results. Green on a scratch control is not candidate success. Keep exact native approval, fresh independent Review and normal delivery. After landing, the ElixirDrops deployment watcher and factory-feature-acceptance worker own production verification and recording on https://app.kogen.studio/workspaces/optimum/projects/elixirdrops/issues/5e6d562d-a1d7-44e0-8d38-8a49d89a1e3a in their authenticated environment; no production or Issue write belongs in Build.
